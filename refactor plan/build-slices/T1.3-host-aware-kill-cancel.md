# T1.3 — host-aware kill/cancel (closes T1-C)

Track A (server). Depends on: T1.1 + T1.2 (shipped — both routes already receive
`getHostConnection: () => hostConnection`). Closes: T1-C. Spec: `foundational-hardening-design.md`
THEME 1 (T1.3, ~line 209) + the T1.2 handoff cancel/kill semantics note.
Reconcile-first: build the host-aware path BESIDE the existing local kill; delete nothing live until proven.

---

## 1. Goal

Make kill/cancel reach the agent host. Killing a host-backed run actually terminates the host child
(no orphaned compute, no `processKilled:false`); `/cancel` cancels a host-backed run that isn't in the
in-process registry instead of 404-ing; workflow-subagent cancel rides the same conduit.

---

## 2. Current behavior (the exact broken paths)

The host protocol ALREADY supports everything we need — no protocol change:
- `{type:'cancel', runId}` → `agent-host-service.ts:392` `cancel()` → `entry.run.cancel()` → kills the spawn
  + arms grace (`agent-run.ts:268-295`). Genuinely terminates host compute.
- `{type:'cancel-workflow-subagent', pcSessionId}` → `agent-host-service.ts:285` → `entry.handle?.kill(reason)`.
- `HostBackedActiveRunHandle.cancel()` (`agent-active-runs.ts:105-107`) already issues `{type:'cancel'}`.

**Broken path A — `/kill` orphans host compute.** `app.post('/api/projects/:projectId/agent-runs/:runId/kill')`
(`agent-runs/routes.ts:228-244`) → `hardKillAgentRun` (`agent-run-control.ts:48`). At `:71` it kills
`row.pid`'s OS tree. But host-backed runs never persist a pid: `persistPid` (`agent-run-factory.ts:989`,
`run.getPid()`) only runs on the in-process legacy `run.on('state')` path; `startHostBackedRun`
(`agent-run-factory.ts:603-746`) never calls `updateAgentRunPid`. So for a host run `row.pid === null` →
`hardKillAgentRun` returns `processKilled:false` (`:53`/`:102`) and the host child keeps running. The graceful
step at `:58-65` only helps if the live `HostBackedActiveRunHandle` is still registered AND its fire-and-forget
host `cancel` lands — neither guaranteed for a phantom/reattached/raced run. = orphaned host compute.

**Broken path B — `/cancel` 404 for non-registry host-backed runs.**
`app.post('.../cancel')` (`agent-runs/routes.ts:210-222`) does `services.getActiveRunRegistry().get(runId)`
and 404s if absent (`:215-216`). Workflow-spawned subagents are tracked in `dag-run-service`
(`hostBackedWorkflowSpawner`, keyed by `pcSessionId`, `dag-run-service.ts:196-264`) and are NEVER registered
in `activeRunRegistry` → guaranteed 404. (A directly-dispatched or boot-reattached host run IS registered —
factory `:705`, reattach `:133` — so those don't 404, but see path C.)

**Broken path C — `/cancel` returns ok but doesn't actually stop (T1.2 live obs).** Even when registered,
`entry.run.cancel()` for a `HostBackedActiveRunHandle` is fire-and-forget (`agent-active-runs.ts:183 issue()`
doesn't await), and the route immediately returns `{ok:true, status:'cancelled'}` (`agent-runs/routes.ts:220-221`)
WITHOUT awaiting the host ack and WITHOUT finalizing the DB row. The row only flips terminal later via the
host's async `run-terminal` event. If the host command races/errors (the swallow at `agent-active-runs.ts:192`)
or the run is a phantom, nothing converges — only `/kill` (which force-finalizes the row, `:78`) makes it
terminal. So `/cancel` "succeeds" but the run lives on.

---

## 3. Target behavior

- **Kill a host-backed run → host child dies.** `/kill` (and the work-item reject kill) routes a host-backed run
  through the live `hostConnection` `sendCommand({type:'cancel', runId})` (awaited), THEN finalizes the DB row.
  No reliance on a (null) `row.pid`; no `processKilled:false` for host runs. Local pid-kill stays for in-process runs.
- **`/cancel` host-cancels a non-registry host-backed run instead of 404.** When the registry has no entry,
  fall back to: is this a host-backed run the host knows about? → `hostConnection.sendCommand({type:'cancel', runId})`.
  Await the ack; on `not-found` from the host AND no registry entry AND no live DB row → 404; otherwise ok.
- **Workflow-subagent cancel rides the same conduit.** A cancel targeting a workflow-spawned subagent issues
  `{type:'cancel-workflow-subagent', pcSessionId}` through `hostConnection` (the spawner already does this
  internally; T1.3 exposes a route-reachable path so the operator/orchestrator can cancel it, closing the
  "killing the agent orphans the parent run" gap from the 004 review).

## 4. Step-by-step changes (reconcile-first)

### 4.1 New host-aware kill in the control service

**`apps/server/src/services/agent-run-control.ts`** — `hardKillAgentRun` (`:48`):
- Add an optional dep `host?: AgentHostReattachClient | null` to `AgentRunControlDeps` (`:27`).
- Before the local pid kill (`:67-74`), if `host` is present, issue `await host.sendCommand({type:'cancel', runId})`
  inside a try/catch (swallow host errors — the local kill + finalize remain the net). This is what actually
  terminates the host child. Make `hardKillAgentRun` `async` (it currently is sync) — see caller updates 4.3.
- Keep the local `killProcessTree(row.pid)` step for the in-process path (pid non-null). For host runs `row.pid`
  is null so that step is a harmless no-op; the host cancel did the real work.
- Report shape: extend `HardKillResult` so `processKilled` reflects EITHER a real local kill OR a successful host
  cancel ack (e.g. add `hostCancelled: boolean`); a host run with a successful host cancel should NOT report a
  misleading `processKilled:false` as "nothing happened". Keep `applyAgentRunTerminalEffects` finalize (`:78`)
  as the idempotent net so the row always converges to `cancelled`.

Reconcile-first note: this ADDS a host branch; the existing local path is untouched for in-process runs. Nothing
deleted.

### 4.2 `/cancel` host fallback in the route

**`apps/server/src/features/agent-runs/routes.ts`** — the cancel handler (`:210-222`):
- Keep the registry lookup first (`services.getActiveRunRegistry().get(runId)`).
- When an entry EXISTS and is a host-backed handle: instead of fire-and-forget `entry.run.cancel()` + optimistic
  ok, route through the SAME host-aware finalize as kill (await host cancel, then finalize) so `/cancel` is no
  longer "ok but didn't stop." Simplest: make `/cancel` for host-backed runs call the host-aware path
  (`hardKillAgentRun` with `host` resolved via `resolveHost()`), OR await `entry.run.cancel()`’s host command +
  reconcile the row. Prefer reusing the host-aware finalize so cancel and kill converge to one code path.
- When NO entry: resolve `const host = resolveHost()`. If a host exists and `getAgentRunRow(runId)` is a
  non-terminal host-backed run, issue `await host.sendCommand({type:'cancel', runId})` and finalize. Only 404 when
  the run is genuinely unknown (no row) — not merely "not in the in-process registry."
- In-process runs with a registry entry keep the existing `entry.run.cancel()` semantics (synchronous, the handle
  drives its own spawn teardown).

DECISION (Q1) — cancel vs kill semantics. RESOLVED: keep them distinct.
`/cancel` = await host `cancel` ack (proves the host received it) but let the host's own terminal event finalize
the row (do NOT force `applyAgentRunTerminalEffects`), so a clean cancel still reports the real terminal status
and a turn-end inside the host's 5s grace honors as completion. `/kill` = force-finalize (the existing hard
semantics). This makes both host-aware while matching the host's built-in cancel grace.

### 4.3 Callers of `hardKillAgentRun` become async

- **`agent-runs/routes.ts` `/kill` handler (`:238`)**: resolve `const host = resolveHost()`; pass it into
  `hardKillAgentRun(runId, { ..., host })`; `await` it (the handler is sync today — make it `async (c) =>`).
- **`apps/server/src/services/agent-run-control.ts`**: signature → `Promise<HardKillResult>`.
- Grep for any other `hardKillAgentRun` callers and await them (work-item reject does NOT call it directly today —
  it calls `rejectAgentWorkItem`; confirm at build whether reject needs host-aware kill or only relies on the
  host `cancel` the reject helper already issues via `hostClient`).

### 4.4 Workflow-subagent cancel route (the same conduit)

INVESTIGATE-AT-BUILD (Q2): confirm whether a workflow-spawned subagent creates an `agent_runs` row and how a
caller would name it (runId vs `pcSessionId`).
- **If it has an `agent_runs` row** targetable by runId: extend the cancel/kill route so a run identified as a
  workflow subagent issues `{type:'cancel-workflow-subagent', pcSessionId}` through `hostConnection` (resolve the
  `pcSessionId` for the run).
- **If NOT first-class** (tracked only by `pcSessionId` in the spawner): extend the workflow-run cancel surface
  (dag-run-service / workflow compat routes) to call the spawner's kill / issue
  `hostConnection.sendCommand({type:'cancel-workflow-subagent', pcSessionId})`. Closes the 004-review
  "killing the sole agent orphans the parent run" gap.
The spawner ALREADY issues the right command internally (`dag-run-service.ts:222-261`, repointed at
`hostConnection` in T1.2) — T1.3 only needs to make it reachable from a cancel action.

### 4.5 Persist the host child pid — NOT doing this

The host owns its children; the server asks the host to cancel rather than reaching across the process boundary to
kill the host's grandchild. Leave `row.pid` null for host runs; the host-aware branch makes it irrelevant.

## 8. Risks

- **`hardKillAgentRun` async** ripples to callers; small — grep all callers + await.
- **Double-finalize race:** host `cancel` triggers an async `run-terminal` AND `/kill` force-finalizes;
  `applyAgentRunTerminalEffects` / `applyHostTerminalSnapshot` idempotency (`agent-host-reattach.ts:296`
  `isDbTerminal`) covers it — do NOT add new dedup. Confirm the existing net holds for cancel-then-terminal.
- **No protocol gap:** host supports `cancel` + `cancel-workflow-subagent` and both truly terminate. If Q2 reveals
  a workflow subagent needs a NEW host command → STOP-and-confirm (current evidence says it does not).
