# T1.2 — single host conduit / event-stream owner

Track A (server). Depends on: T1.1 (shipped). Closes: T1-D. Spec: `foundational-hardening-design.md` THEME 1 (T1.2) + the two 2026-06-01 CORRECTION notes.
Reconcile-first: wire the new path → verify → THEN delete the old patch/client, in that order, within this slice.

## 1. Goal + one-line win

Make the ONE `hostConnection` the sole conduit for BOTH commands AND the event stream, for ALL live host consumers.

**Win:** every host consumer self-heals after a host respawn (no consumer left on the frozen `agentHostClientForDispatch`); ONE ordered multiplexed event stream feeds reattach + factory + sweep + spawner; the `latestRunStateSnapshot` race patch is gone.

Two moves carry it:
- Repoint the three remaining frozen-client consumers (sweep, mcp-bridge, ProjectRegistry/factory) at `hostConnection` (self-healing `sendCommand`/`refreshRuns`).
- Migrate the four terminal-event consumers to `hostConnection.onEvent` (persistent, survives reconnect) so there is one stream, then delete the per-dispatch replay patch.

## 3. Target wiring

ONE `hostConnection` (already constructed `index.ts:265`, before boot reattach ~449) is the conduit:

- **commands/refresh:** sweep, mcp-bridge, ProjectRegistry→factory→spawner all call `hostConnection.sendCommand`/`refreshRuns` (self-healing).
- **events:** ONE multiplexed `hostConnection.onEvent(...)` emitter feeds:
  - boot reattach (persistent, process-life) — `run-state`/`run-terminal`/`run-jsonl`.
  - per-dispatch factory (per-run, unsubscribed on terminal) — same types, filtered to its `runId`.
  - workflow spawner (per-subagent, unsubscribed on settle) — `workflow-subagent-*`, filtered to its `pcSessionId`.
  - sweep does NOT subscribe (polling reconcile — correctness net).

**Listener lifetimes / unsubscribe (critical — `onEvent` returns an unsub; leaking = listener buildup):**
- boot reattach: subscribe ONCE at boot; never unsubscribe (process-life). One listener total.
- factory: `unsubscribe = hostConnection.onEvent(...)`; MUST call `unsubscribe()` on terminal-applied AND on every `fail()` path (both already wired at `:624/:648`). Unchanged — just the emitter source changes from the frozen client to `hostConnection`.
- spawner: `unsubscribe` cleared in `cleanup()` on `settle()` (already wired `:159-171`). Unchanged source-of-truth; only the emitter changes.

**Multiplexing safety:** `hostConnection.onEvent` fans every event to every listener. Segregation is by event-type + id-filter already present in each consumer:
- factory filters by `runId` (`hostEventBelongsToRun`), spawner filters by `pcSessionId`, boot reattach keys its local `handles` Map by `runId`. No cross-talk.
- **Double-apply guard:** boot reattach (persistent) AND the factory (per-run) both see the SAME `run-terminal` for a factory-dispatched run. `applyHostTerminalSnapshot` is idempotent (`agent-host-reattach.ts:296` `if (!row || isDbTerminal(row.status)) return 0`) — the second caller no-ops. This is the EXISTING net; do not add new dedup. (Today they're on separate streams; after this slice they share one — the idempotency still covers it because the DB row flips terminal on first apply.)

### `apps/server/src/services/agent-run-server-boot.ts` + `agent-host-reattach.ts` (4a — boot reattach onto `hostConnection`)

Boot reattach does two things on its client: (a) enumerate existing runs (`listRuns()` after the boot client's `hello`), (b) register a persistent `onEvent` (`agent-host-reattach.ts:148`).

**Decision (justified §6): route boot reattach's event subscription + run enumeration through `hostConnection`** so there is truly ONE stream.
- In `index.ts` boot block: before calling `reattachAgentRunsDuringServerBoot`, `await hostConnection.refreshRuns()` so the connection is connected + has the run cache.
- Pass `getHostClient: () => hostConnection` into `reattachAgentRunsDuringServerBoot` (its `AgentRunServerBootDeps.getHostClient` already accepts `() => AgentHostReattachClient | null`, `agent-run-server-boot.ts:28`). This replaces the default `resolveAgentHostClientForBoot` — so the boot client IS `hostConnection`. `reattachAgentRunsOnBoot` then calls `hostConnection.listRuns()` (`:97`) + `hostConnection.onEvent(...)` (`:148`) — the persistent subscription is now on the shared emitter.
- `result.mode === 'host'` still returns; `result.hostClient` === `hostConnection`. Either stop assigning `agentHostClientForDispatch` (delete) or assign a `hostMode = true` flag (§6).

Caveat: `hostConnection.refreshRuns()` must run BEFORE `reattachAgentRunsOnBoot` reads `listRuns()` — `refreshRuns` connects lazily + populates the cache, and `reattachAgentRunsOnBoot` is synchronous and reads the cache. Sequence in the boot block: `await hostConnection.refreshRuns().catch(()=>{})` → `reattachAgentRunsDuringServerBoot({ getHostClient: () => hostConnection, ... })`. If no host is live at boot, `refreshRuns` leaves the cache empty → reattach finds no host runs → `mode === 'host'` with zero registered (acceptable; the heartbeat reconnects later, the sweep + factory pick up runs). NOTE: if `refreshRuns` connected nothing, `result.hostClient.listRuns()` is empty but `getHostClient` returned non-null, so `mode==='host'` — that's correct for an always-on host that's mid-respawn.

## 5. `latestRunStateSnapshot` deletion — proof-before-delete

The patch (`agent-run-factory.ts:614-618`, `:656`, `:706`) exists because a `run-state` (incl. `running`) can fire during the `await sendCommand` window, BEFORE `handle` is assigned — and on separate streams ordering wasn't guaranteed, so the start-run seed could be left stale.

**Why a single ordered stream makes it unnecessary:** `hostConnection.onEvent` is fed by ONE inner `/events` stream in `seq` order, and `seedLastSeq` continuity means no reordering across reconnect. The factory subscribes BEFORE `sendCommand` (`:628` precedes `:663`), so any `run-state` during the await is delivered to the listener in order. After `handle` is assigned (`:697`), subsequent `run-state` events apply directly (`:657 if (handle) handle.applySnapshot`). The only gap the patch covered was an event arriving while `handle === null`.

**Proof-before-delete sequence (reconcile-first, same slice):**
1. Wire all of §4 (consumers on `hostConnection`), KEEPING the patch.
2. Run the new unit test (§6 test 2): a `run-state:running` emitted on `hostConnection` DURING the `sendCommand` await is correctly reflected on the handle AFTER assignment — assert with the patch REMOVED in the test path (inject a connection that emits mid-await). Prove the handle ends with the running snapshot via in-order delivery alone.
3. Live-verify a fresh dispatch reaches `running` on the UI (active-session bar) with the patch removed.
4. THEN delete `:618` (`let latestRunStateSnapshot`), the `:656` assignment, and the `:706` replay. The `run-state` branch becomes just `if (handle) handle.applySnapshot(event.run);`.

If step 2/3 reveal a real window (handle null when the event lands and no later event re-asserts), KEEP the patch and log the finding — do not force the delete.

## 6. Decisions

**D1 — boot reattach consumes `hostConnection` (not its own boot client).** Justified: the brief's preference + the design's "one stream" goal. `hostConnection` is up at `:265` before boot (~449); `refreshRuns()` covers enumeration; routing the persistent `onEvent` through the shared emitter means truly one stream. Cost: one ordering caveat (refresh before reattach), handled in §4a.

**D2 — host-mode discriminator after dropping the frozen client.** `agentHostClientForDispatch` truthiness gates the liveness sweep (`:553`) and the reconcile sweep. After D1, `result.mode === 'host'` from boot reattach is the authoritative host-mode signal. **Replace `let agentHostClientForDispatch` with `let hostMode = false`**, set `hostMode = (result.mode === 'host')` in the boot block. Sweeps gate on `hostMode`. Do NOT gate on `hostConnection.isConnected()` — the host is always-on but may be mid-respawn (disconnected) while still in host-mode; `isConnected()` would wrongly hand non-terminal rows to the in-process liveness sweep during a respawn window.

**D3 — delete `agentHostClientForDispatch` for live use.** After D1+D2, nothing reads it: `:290`→`hostConnection`, `:516`→`hostConnection`, `:588`→`hostConnection`, `:553`→`hostMode`, `:456` assign removed (replaced by `hostMode`). Confirmed via grep: the only readers are those five sites + the declaration. Delete the `let agentHostClientForDispatch` declaration (`:257`) and its `AgentHostReattachClient` import if now unused (it's still used as a type in routes — keep the import, drop the var). `resolveAgentHostClientForBoot` (`agent-host-client.ts`) is no longer called by `index.ts` (boot now passes `getHostClient: () => hostConnection`) but STAYS in the codebase (still exported/tested; deleting it is out of scope — name as a follow-up cleanup if dead).

**D4 — keep `applyHostTerminalSnapshot` idempotency as the net.** No new dedup. The shared emitter + idempotent terminal application + the existing per-run/per-subagent filters cover double-delivery during reconnect re-subscribe.

## 11. Risks

- **Listener leak (highest):** the factory + spawner MUST unsubscribe on terminal/settle/fail. Source moved from frozen client to `hostConnection` (a longer-lived emitter) → a missed unsub now leaks for process life, not just the dead client's life. Test #5 guards it; audit every `fail()`/`settle()`/terminal path keeps its unsub.
- **Boot ordering:** `hostConnection.refreshRuns()` must complete before `reattachAgentRunsOnBoot` reads `listRuns()` (sync). Ordered explicitly in §4a. If skipped, boot reattach silently registers zero runs (recovered later by sweep/heartbeat — degraded, not broken).
- **Double-delivery window on reconnect re-subscribe:** `/events?after=lastSeq` can replay an applied terminal. Covered by `applyHostTerminalSnapshot` idempotency + `lastSeq` continuity. No new dedup.
- **Workflow-spawner key:** spawner routes by `pcSessionId` (`dag-run-service.ts:201`); run events route by `runId`. Distinct event-type sets + distinct keys → no cross-talk on the shared emitter. Verify the filter at build (test #4).
- **Host-mode discriminator regression:** if `hostMode` is computed wrong, BOTH the reconcile sweep and the in-process liveness sweep could run (double-owner) or neither (phantom runs). D2 ties it to `result.mode === 'host'` — the same authoritative signal the boot path already used. Confirm exactly one sweep owns non-terminal rows post-change.
- **Deleting the patch too early:** strictly gated by §5 steps 2-3; if the mid-await window is real, keep the patch + log.
